# llm-wiki-vault

这是一个使用 Obsidian 与轻量 LLM Wiki 方法维护的个人知识库，目标是把供应链业务、技术架构、AI 应用、项目经验和专题研究沉淀为可追溯、可复核、可跨项目复用的长期知识。

知识库不追求自动收集一切，也不把单个项目经验直接包装成行业规律。它负责审核来源、去重、外部核验、冲突检查和适用范围抽象。

## 目录结构

| 位置 | 用途 |
|---|---|
| `raw/` | 原始资料，只读；禁止修改、移动、删除、重命名或覆盖 |
| `wiki/` | 稳定概念、业务知识、技术知识和经过审核的可复用经验 |
| `wiki/_meta/` | 生命周期、来源目录及其他治理规则 |
| `wiki/_templates/` | 主题笔记、项目复盘和技术架构模板 |
| `wiki/供应链基础/` | 供应链基础概念、参考模型和通用业务框架 |
| `wiki/物流规划/` | 物流网络、节点、资源和规划方法 |
| `wiki/运输履约/` | 运输对象、配载、路线、预约、状态与异常机制 |
| `wiki/企业实践/` | 企业案例、变革经验及其证据边界 |
| `wiki/数字化与AI/` | 供应链数字化、算法和 AI 应用 |
| `outputs/` | 审计、阶段报告、一次性分析和必要快照，不作为权威知识源 |

未来确有内容时，可以增加 `patterns/` 或 `playbooks/`；当前不为追求目录完整而创建空目录。

## 新资料如何进入知识库

1. 将原始资料保存在 `raw/`，之后保持只读。
2. 在来源目录登记来源、时间、类型、可信度和已知限制。
3. 识别可复用主题，不按原文目录机械生成页面。
4. 区分来源事实、分析推断、建议和待核验内容。
5. 为关键结论添加页码、章节、段落或外部官方链接。
6. 检查现有 Wiki，执行去重、合并、冲突和时效检查。
7. 更新主题双链与 `wiki/INDEX.md`。

## 外部项目候选如何晋升

外部项目应保存完整事实、代码证据、客户约束和过程记录，并只向本知识库提供经过脱敏、抽象的“知识晋升候选”。候选进入正式知识库前，还需要：

1. 确认来源和证据状态。
2. 检查脱敏及跨项目复用价值。
3. 与现有知识去重并检查冲突。
4. 对标准、行业、版本及时效敏感结论进行外部核验。
5. 决定新建、合并、补充、保留候选或拒绝晋升。

候选文件可以继续保留在来源项目中，由知识库按绝对路径只读审核；不要求复制进本仓库，也不允许个人知识库反向修改来源项目事实。

## 项目事实与通用知识的边界

留在来源项目中的内容：

- 客户专属流程、配置和验收口径。
- 源代码、内部接口、账号、地址及环境信息。
- 完整代码证据、上线状态、故障过程和项目决策上下文。

可以晋升的内容：

- 已脱敏且可跨项目复用的概念、模式、方法、检查表和反模式。
- 明确适用条件、不适用条件和证据强度的经验。
- 经权威来源核验的行业、标准和版本结论。

暂时无法证明通用性的内容继续保留为候选，不急于进入正式 Wiki。

## DACHENG 示例

`D:\Java-Project\DACHENG` 是 TAK SCMP 项目仓库，也是当前第一个外部来源项目。完整事实和证据保存在该项目的 `docs/project-retrospective/`，脱敏候选保存在 `07-知识晋升候选/`。个人知识库只负责读取候选、审核和正式晋升，不替代项目复盘，也不反向修改项目事实。

DACHENG 只是首个示例，不是唯一来源。其他项目、需求开发、故障排查、架构设计、技术研究、业务研究、书籍和行业资料都可以按同一套规则进入审核流程。

## 当前限制与下一步

- 当前原始资料较少，部分二手资料可信度有限。
- 企业案例仍缺少更多官方或独立来源交叉验证。
- 项目晋升流程已经由首个“订单—运输履约链”案例完成全流程验证；后续仍需通过更多项目检验其稳定性和适用边界。
- WMS、OMS、TMS、MDM、跨域一致性和 AI 工程实践仍需依靠真实项目逐步沉淀。
- 后续优先吸收高质量候选并完善已有主题，不提前生成大量空洞页面或目录。

完整维护规则见 [AGENTS.md](AGENTS.md) 与 [知识库维护规则](wiki/_meta/知识库维护规则.md)。
