# 运输履约状态与变更传播

订单、运输需求、计划、运单、预约和异常拥有不同生命周期；跨对象变更不能靠复制同一个状态值完成，而应明确动作语义、前置条件、数量与资源副作用、传播方向和失败补偿。

**状态**：草稿  
**最后更新**：2026-07-07  
**复核触发条件**：补充跨系统状态传播的权威资料或新的项目验证；对象生命周期、事件契约变化

## 状态分离

- 到达不等于作业完成，作业完成也不等于离场。
- 单票运单完成不等于订单全部履约，必须按需求数量和允许的终止量聚合。
- 预约取消不必然取消运单；车辆改派也不必然改变需求数量。
- 异常是需要处理的业务对象或事件，不能简单等同于主对象“失败”。

这些结论来自脱敏项目复盘与领域分析；候选引用的 SAP Change Controller 可支持“运输对象变化需要协调”的方向，但不足以证明一套通用状态机，因此本文暂定为草稿。[来源:SRC-003，候选知识6]

## 动作语义

| 动作 | 典型含义 | 必须检查的副作用 |
|---|---|---|
| 撤销 | 回退尚未生效或尚未执行的操作 | 释放原分配、保留审计链 |
| 取消 | 终止后续履约 | 数量终止、资源释放、上游回写 |
| 改派 | 更换车辆、司机或承运方 | 原资源解绑、新资源校验、预约影响 |
| 改期 | 更换预约或计划时窗 | 原容量释放、新容量占用、后续站点重算 |
| 异常关闭 | 对差异给出最终处置 | 挂账量转移、责任与凭证完整 |

## 传播规则模板

每个动作至少定义：发起对象和权限、允许的源状态、幂等键、数量变化、资源变化、预约影响、下游命令或事件、上游聚合回写、失败补偿、超时处理及审计证据。

当前状态适合查询；不可变业务事件适合追溯。是否采用完整事件溯源应按审计和重放需要决定，不能因为需要历史记录就默认引入复杂基础设施。（分析）

## 异常与一致性

- 同一对象内使用事务和条件更新保证状态前置条件。
- 跨服务传播应允许重试并以业务键幂等消费。
- 局部失败时记录待补偿状态，不伪装为整体成功。
- 聚合状态由明细事实和明确规则计算，并保存计算版本或依据。

具体采用 Outbox、Saga 或对账补偿，取决于一致性时限和基础设施；当前候选没有足够外部证据支持统一技术处方。（分析，待核验）

## 设计检查

1. 每个状态属于哪个对象，是否存在同名异义？
2. 每个动作的数量、资源和预约副作用是否明确？
3. 重复、乱序和延迟事件是否会破坏结果？
4. 单票完成如何聚合成需求或订单完成？
5. 失败后由谁发现、重试、补偿和人工接管？
