# 运输履约对象模型

运输履约应区分订单、运输需求、运输计划、运单和执行实绩；这些对象分别承载客户承诺、待组织工作量、资源与路线方案、执行任务和实际结果，不能仅用一条“订单到运单”的状态链替代。

**状态**：已核验  
**最后更新**：2026-07-07  
**复核触发条件**：新增运输模式、结算边界、跨域变更规则或新的权威产品模型

## 对象职责

| 对象   | 主要回答                | 不应承担        |
| ---- | ------------------- | ----------- |
| 订单   | 客户承诺了什么             | 直接表示车辆执行任务  |
| 运输需求 | 哪些货量、地点和时窗需要被组织运输   | 固化最终路线和承运资源 |
| 运输计划 | 如何组合需求、安排站点、时窗和资源   | 冒充实际执行结果    |
| 运单   | 哪项任务已经进入执行          | 覆盖全部上游需求历史  |
| 执行实绩 | 实际何时、何地、完成多少、发生何种异常 | 反向改写原始承诺    |

SCOR DS 将 Order、Plan 和 Fulfill 分为不同流程；SAP 和 Oracle 的产品模型也分别使用可计划需求与执行运输对象。它们支持“分层有价值”，但对象名称和粒度不是统一行业标准。[外部核验:ASCM SCOR DS，2026-07-07访问](https://www.ascm.org/corporate-solutions/standards-tools/scor-ds/) [外部核验:Oracle Order Releasing Process，2026-07-07访问](https://docs.oracle.com/en/cloud/saas/transportation/25c/otmol/planning/order_manager/create_order_release.htm)

## 关系机制

- 一个订单可产生多个运输需求，例如按发货地、时窗或货物约束拆分。
- 多个需求可合入同一计划或运单；一个需求也可分批进入多个计划或运单。
- 计划确认不等于执行完成；实际数量、到离站时间和异常应由实绩记录。
- 对象之间应保存可追溯的明细关系，不能只在上游对象上累计一个“已配载量”。

上述关系是对项目实践与官方产品模型的归纳，不是 SCOR 的规定。（分析）具体数量机制见 [[02-运输合单拆单与数量守恒]]。

## 适用边界

适用于存在合单、拆单、分批运输、资源分派或执行跟踪的运输业务。对于低频、一次性且无调度和过程跟踪要求的简单运输，可合并部分对象，但仍要明确承诺、计划和实绩字段的语义。

## 设计检查

1. 每个对象是否有唯一业务责任和生命周期？
2. 一单多运、多单一运和部分履约能否由明细关系表达？
3. 计划值、预约值和实际值是否分开保存？
4. 取消、短少和改派后能否追溯原分配记录？
5. 聚合状态是否由明细事实推导，而不是人工文案覆盖？
