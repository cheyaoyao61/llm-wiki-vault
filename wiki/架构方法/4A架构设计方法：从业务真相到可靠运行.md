# 4A架构设计方法：从业务真相到可靠运行

4A 架构设计在本文中指业务架构、数据架构、应用架构和技术架构四层递进方法：先用业务架构定义业务真相，再用数据架构定义事实载体，再用应用架构定义能力承载，最后用技术架构保障可靠运行。它适用于 SCM、3PL、制造物流等多域协同项目，也可抽象到其它业务系统项目；关键是不要从微服务、数据库表、页面菜单或技术选型开始。

**状态**：已核验  
**最后更新**：2026-07-08  
**复核触发条件**：新增跨域架构项目复盘；服务拆分、可靠消息、对账补偿或上线策略被新项目证据推翻；4A 语境或组织架构方法发生变化

## 四层关系

| 架构层  | 定义   | 核心问题                       | 主要产物                                        |
| ---- | ---- | -------------------------- | ------------------------------------------- |
| 业务架构 | 业务真相 | 业务为什么存在、谁参与、哪些链路必须闭环       | 业务域、角色、业务链、能力地图、场景优先级、上线边界                  |
| 数据架构 | 事实载体 | 哪些对象承载事实、对象归谁、数量和状态如何可信    | 核心对象、对象归属、数量账、状态机、主数据、数据流、指标口径              |
| 应用架构 | 能力承载 | 哪些系统、服务、模块和端侧承载业务能力        | 逻辑分域、物理服务、模块边界、任务中心、接口治理、端侧能力               |
| 技术架构 | 可靠运行 | 接口、事件、事务、补偿、监控、测试和上线如何保障闭环 | 同步/异步边界、事务边界、幂等、可靠消息、补偿、对账、权限、配置、监控、测试、灰度上线 |

这四层不是四张互不关联的图，而是逐层约束关系。业务架构没有说清，后面的服务、表和消息会把不清楚的业务事实固化成系统债；技术架构不可靠，前面的业务闭环也只能停在文档上。（分析）[来源:SRC-007，候选知识1]

## 通用方法

任意业务系统项目都先按以下顺序设计：

1. 业务架构：识别业务目标、参与者、核心业务链、完成条件和异常流。
2. 数据架构：识别核心对象、对象所有权、状态机，以及数量、金额、额度、积分、余额等守恒关系。
3. 应用架构：决定系统、服务、模块、端侧、报表和外部接口如何承载业务能力。
4. 技术架构：设计技术实现、可靠性、权限、监控、测试和上线策略。

不要从“用不用微服务”“建哪些表”“做几个菜单”“选什么消息队列”开始。技术选型是实现手段，不是业务边界证据。（分析）[来源:SRC-007，候选知识1、3、11]

### 业务架构

- 先定义业务目标和成功标准，而不是先定义系统范围。
- 识别真实参与者：谁提出需求、谁承诺、谁执行、谁复核、谁处理异常、谁有权人工豁免。
- 用端到端业务链表达范围：输入、动作、对象变化、完成条件、异常、逆向和对账。
- 场景优先级按业务闭环排序：不做会导致履约失败、账不准、异常不能恢复的是 P0；只影响效率或体验的是 P1；算法、智能分析和高级报表通常是 P2。（建议）[来源:SRC-007，候选知识6]

### 数据架构

- 先定义对象，不先建表。
- 每个核心对象必须有主责方；综合视图可以汇总事实，但不应替事实拥有方写入事实。
- 数量、金额、额度等必须先形成互斥账，再设计状态和报表。
- 状态应由事件、数量和完成条件解释，不能替代事实本身。
- 指标口径必须能追溯到业务对象和事件，不能只从页面状态推导。（分析）[来源:SRC-007，候选知识3、4、9]

### 应用架构

- 先做逻辑分域，再决定物理服务拆分。
- 系统、服务、模块、端侧和报表都是能力承载，不是业务事实本身。
- 外部接口要把外部格式转换为内部业务命令，不应绕过核心对象直接改状态。
- PC、PDA、移动端、小程序等端侧入口可以不同，但同一业务必须调用同一套规则。
- 报表和 Agent 必须建立在可靠业务事实之上；底层事实不准，上层智能只是把错误包装得更像结论。（分析）[来源:SRC-007，候选知识9、10]

### 技术架构

- 同步接口用于需要立即校验和返回业务结果的命令；领域事件用于通知事实已经发生。
- 跨域一致性优先采用本地事务、可靠事件、幂等消费、状态回执、补偿对账和人工接管，不默认追求重型分布式事务。（建议）[来源:SRC-007，候选知识7]
- 关键命令和事件应具备业务键、版本、来源、幂等键、发生时间和链路追踪。
- 监控不只看服务存活，还要看业务积压、消息失败、账不平、异常超时和对账差异。
- 上线方案必须说明灰度范围、切回方式、新老系统责任和对账机制。

## SCM/3PL特化方法

SCM/3PL 项目的复杂点在于订单、仓储、运输、库存、结算和主数据同时协作，业务成败不取决于某个系统页面是否完成，而取决于履约链、数量账、状态机和异常恢复能否闭环。（分析）[来源:SRC-007，候选知识1、8]

### 业务架构重点

- 检查订单、仓储、运输、库存、结算、主数据是否形成履约闭环。
- 订单链要说明需求来源、确认、变更、取消和向下游派生。
- 仓储链要说明入库、出库、库存、库内作业、盘点和差异处置。
- 运输链要说明需求、计划、运单、预约、在途、签收、异常和回单。
- 结算链要基于业务实绩、费用规则和对账，不应反向定义履约事实。
- 首期上线范围应按业务链定义，不应只说“上线某系统”。[来源:SRC-007，候选知识8]

### 数据架构重点

SCM/3PL 数据架构至少要明确以下对象归属：

| 对象类型 | 设计问题 |
|---|---|
| 订单 | 谁拥有需求承诺、变更、取消和综合视图 |
| 库存 | 谁拥有库存行、数量状态、冻结占用、库存事务和履历 |
| 任务 | 任务计划、执行实绩和账务事件是否分开 |
| 运单 | 谁拥有运输计划、司机车辆、在途、签收和异常 |
| 预约 | 是否有时间资源占用、改期和容量约束 |
| 盘点 | 是否有快照、实盘、差异、确认和落账 |
| 结算 | 是否基于已确认业务实绩，而不是未闭环状态 |
| 主数据 | 客户、供应商、物料、包装、仓库、库位、承运资源是否在业务前置环节被校验 |

数量账要优先于状态字段。订单需求、库存占用、作业实绩、装运、出账、运输执行、取消和异常待处理应形成互斥数量桶；累计字段可以用于查询，但必须能由明细重算。（分析）[来源:SRC-007，候选知识4]

### 应用架构重点

- OMS/WMS/TMS/MDM/BMS 等系统名只能作为常见能力承载示例，不能替代对象所有权分析。
- 接口服务是否独立，要看外部系统数量、协议复杂度、版本映射、多租户、审计重放和运维责任；必须有接口治理能力，但不一定首期就独立拆服务。（分析）[来源:SRC-007，候选知识10]
- 协同门户是否建设，要看供应商、承运商、客户是否真实进入系统；如果实际由内部人员代操作，就应设计代操作、通知和审计，而不是空置门户。（建议）[来源:SRC-007，候选知识6、10]
- PDA、PC、司机端等端侧能力必须贴近现场角色、设备、网络和作业节奏；现场不能长期稳定维护的粒度，不应成为主账闭环强依赖。（分析）[来源:SRC-007，候选知识5]

### 技术架构重点

- 跨域事件必须配套幂等、失败重试、死信、补偿和业务对账；消息队列只降低同步依赖，不自动保证业务一致。（分析）[来源:SRC-007，候选知识7]
- 同步接口和异步事件可以混用，但每个跨域动作都要说明调用方、事实拥有方、幂等键、成功事件、失败事件和人工补偿入口。
- 新老系统并行时，要明确哪些订单类型、仓库、运输场景、库存动作和结算动作由新系统负责。
- 业务对账是恢复机制，不是报表锦上添花。

## 服务拆分决策

开发前先做逻辑分域，再根据边界证据、上线节奏、一致性模型和团队能力决定是否物理拆服务。服务拆分的核心不是“服务数量”，而是谁拥有业务事实、谁发布事件、谁消费命令、失败后谁补偿。（分析）[来源:SRC-007，候选知识3、11]

| 条件 | 推荐形态 |
|---|---|
| 业务边界清楚、对象生命周期不同、上线节奏不同、可接受最终一致，且团队能支撑测试、部署、监控和补偿 | 物理拆成多个服务 |
| 业务边界清楚，但工程能力、测试能力、运维能力或补偿能力不足 | 逻辑分域，物理单体或更粗粒度服务 |
| 业务边界不清，流程仍频繁变化 | 模块化单体优先，先固化领域模型和接口契约 |
| 强事务耦合多，跨域状态高度同步 | 单体或粗粒度服务优先，避免过早制造分布式事务 |

服务拆分后还要检查：是否直写其它服务数据、是否存在多个状态入口、是否有可靠事件、是否有幂等和补偿、是否能独立回放失败事件。拆开服务不等于边界清楚；边界不清时使用消息、接口或微服务只会把问题分散到更多地方。（分析）

## 检查表

### 通用4A检查

- [ ] 是否先定义业务目标、参与者、业务链、完成条件和异常流？
- [ ] 是否明确每个核心对象的所有者？
- [ ] 是否定义数量、金额、额度等守恒关系？
- [ ] 状态机是否按对象拆分，并有触发事件、前置条件和副作用？
- [ ] 应用边界是否来自业务事实，而不是页面、菜单或组织部门？
- [ ] 同步接口和异步事件的使用边界是否清楚？
- [ ] 跨域动作是否具备幂等、重试、补偿和对账？
- [ ] 监控是否覆盖业务异常，而不仅是服务健康？
- [ ] 上线范围是否按业务链、对象和责任描述？

### SCM/3PL检查

- [ ] 订单、仓储、运输、库存、结算、主数据是否形成端到端闭环？
- [ ] 订单、库存、任务、运单、预约、盘点、结算对象是否有主责域？
- [ ] 出库、入库、运输、盘点是否都有互斥数量账？
- [ ] 仓储现场作业粒度是否经过角色、设备、扫码条件和作业节奏验证？
- [ ] PC、PDA、司机端、门户是否调用同一业务规则？
- [ ] 外部接口是否有日志、幂等、重放、映射版本和异常隔离？
- [ ] 跨 OMS/WMS/TMS/MDM/BMS 的事件是否有补偿和对账？
- [ ] 首期简化能力是否记录人工兜底者、放弃能力、数据债务和升级触发器？
- [ ] 报表和 Agent 是否建立在可靠业务事实、事件和指标口径之上？

## 常见反模式

- 把 4A 当成四张互不关联的图。
- 跳过业务架构，直接画微服务。
- 跳过数据架构，直接建表和状态字段。
- 把用了 Kafka、Feign、微服务、配置中心当成架构优点，而不追问失败后业务如何恢复。
- 把报表、数据中台或 Agent 放在业务事实可靠之前。
- 用系统名定义上线范围，而不是用业务链定义上线范围。
- 用一个状态字段同时表达生命周期、作业处理、冻结占用和完成情况。
- 只画正常流程，不画异常、逆向、补偿和对账。
- 首期简化后不记录适用条件，导致临时方案被误认为完整产品能力。

## 项目事实边界

以下内容只属于来源项目事实或阶段性取舍，不应泛化为行业标准：

- 某个业务域能上线，只能证明它在特定范围、组织方式、人工兜底和数据条件下可运行，不证明架构已经成熟。[来源:SRC-007，候选知识2]
- 某个仓储链未上线，不能被简化为“微服务不适合”或“架构完全失败”；应回到业务粒度、数量账、状态所有权、异常补偿、测试收口和实施范围分别分析。（分析）[来源:SRC-007，候选知识2、5]
- 人工调度、内部代操作、门户未使用、未独立接口服务、结算未独立服务、数据智能仍处蓝图阶段等，都是特定组织和阶段事实，不能外推为其它项目也应如此。[来源:SRC-007，候选知识6、9、10]
- 某类标签、PDA 或 PC 作业模式在来源项目中遇到适配问题，不代表所有仓库都应采用或放弃该模式；下次项目必须重新验证现场粒度。（分析）[来源:SRC-007，候选知识5]

## 适用边界

适用：

- 多业务域、多系统、多团队协作的企业应用项目。
- SCM、3PL、制造物流、ERP 周边、订单履约、库存、运输、结算等需要跨域一致性的项目。
- 开发前需要决定系统边界、服务拆分、接口事件和上线策略的项目。
- 项目复盘、架构评审、方案评审和重构前诊断。

不适用或需简化：

- 低频、单用户、单对象、无跨系统协作的简单台账。
- 一次性脚本、临时数据修复或探索性原型。
- 已有成熟产品形态且只做轻量配置的项目；这类场景仍可用 4A 做风险检查，但不必完整展开。
- 法规、安全或实时控制系统；本文不替代专门的合规、安全、实时性和安全工程方法。
